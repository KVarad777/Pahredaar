Build order in Colab:
1.  velocity_store.py  — a simple dict-of-deques or pandas groupby-rolling simulation is fine for a 
hackathon; you don't need Redis. Just make sure it's incremental (update after each txn) not 
recomputed by scanning full history — even simulated, structure the code this way so you can honestly 
say "incrementally updated" in your pitch.
2.  graph_state.py  — use networkx  for simplicity in Colab. Nodes = accounts/devices/IPs, edges 
added as transactions occur. Compute degree/centrality by reading current graph state, not rebuilding 
the graph each time.
3.  behavioral_baseline.py  — rolling mean/std of amount and login-hour per account, updated after 
each txn.
4.  feature_assembler.py  — concatenates transaction fields + identity fields + velocity + graph + 
behavioral + missingness flags into one row. This row is what both GBM and the ensemble consume.
Validation checkpoint: before training anything, print a handful of assembled feature vectors and sanity-
check them by eye — do velocity counters actually increase across a session, does a new account correctly 
show is_new_account=true  and centrality=0? Bugs here silently corrupt every downstream model.

held-out scenario type gets near-zero recall, that's actually a good diagnostic signal for your round-1 
baseline — it's exactly what the reward loop is supposed to improve over rounds. Don't panic if round 1 is 
bad; that's the story you want to tell.
Phase 6 — Reward system (Red vs Blue self-play)
 
This is your novelty claim, so implement it as literally as your spec describes — a scored selection loop, not 
full RL.
# blue_reward.py
def blue_reward(recall_new_techniques, fpr, latency_penalty, w1=1.0, w2=1.0, w3=0.3):
    return w1 * recall_new_techniques - w2 * fpr - w3 * latency_penalty
# red_reward.py
def red_reward(blue_detection_rate_on_scenario, structural_novelty_score, w1=1.0, w2=0.5):
    return w1 * (1 - blue_detection_rate_on_scenario) + w2 * structural_novelty_score
